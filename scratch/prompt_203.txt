## 8. Entitlement Architecture (the core logic)

Compute **effective access** server-side from three independent layers — never from a single frontend boolean:

| Layer | What it is |
|---|---|
| **A. Automatic Entitlement** | Comes from the existing payment/subscription system, untouched by this feature |
| **B. Manual Admin Entitlement** | An access grant the Admin created directly (with its own start/expiry/lifetime) |
| **C. Admin Override/Restriction** | An explicit Admin "OFF" that blocks access regardless of A or B |

**Resolution rules:**

| Automatic (A) | Manual (B) | Override (C) | Effective Access |
|---|---|---|---|
| Active | — | — | **ON** |
| Active | — | OFF | **BLOCKED** (subscription itself is preserved, untouched, days not consumed) |
| Active (10 days left) | — | OFF → later cleared | **ON**, resumes with the same 10 days remaining |
| None | Active until expiry | — | **ON** until manual expiry |
| None | Active, Lifetime | — | **ON** until Admin manually disables it |

- Manual access always runs *alongside* automatic entitlement, never replacing it.
- When a manual grant's expiry date/time passes, it deactivates automatically; the Admin can re-enable it later.
- Admin can change ON/OFF, Start Date, Expiry Date, or switch to Lifetime at any time.

**Admin-only detail view example** (never shown to the end user):

```
Automatic:         None

```

## 14. Suggested Minimal Data Model *(illustrative — adapt to what you find during inspection; do not duplicate existing fields)*

```prisma
// Extends the existing User model — don't duplicate profile/email/username
model User {
  // ...existing fields (id, email, name, username, image, createdAt, etc.)
  displayId      String?        @unique   // "USER-0001", assigned once, backend-generated
  accountStatus  AccountStatus  @default(ACTIVE)
  lastLoginAt    DateTime?
  accessGrants   AccessGrant[]
  accessLogs     AccessAuditLog[]
}

enum AccountStatus { ACTIVE SUSPENDED BANNED }
enum AccessType    { COURSE PRO PREMIUM }
enum GrantSource   { MANUAL OVERRIDE }   // automatic entitlement stays in the existing subscription model

model AccessGrant {
  id         String      @id @default(cuid())
  userId     String
  user       User        @relation(fields: [userId], references: [id])
  type       AccessType
  source     GrantSource            // MANUAL grant vs explicit OFF override
  isActive   Boolean     @default(true)
  startDate  DateTime?
  expiryDate DateTime?              // null + isLifetime = lifetime
  isLifetime Boolean     @default(false)
}

model AccessAuditLog {
  id           String     @id @default(cuid())
  userId       String
  user         User       @relation(fields: [userId], references: [id])
  type         AccessType
  previousState String
  newState     String
  startDate    DateTime?
  expiryDate   DateTime?
  isLifetime   Boolean
  adminId      String
  createdAt    DateTime   @default(now())
}
```

Effective access for each `AccessType` = compute in a single server-side function combining the existing automatic-subscription check + any active `MANUAL` grant + any active `OVERRIDE` (override wins if present, per §8's table).
