# MASTER DEBUG + FIX PROMPT — User Data Not Syncing Across Devices (Journal)
**Target system:** Cycle of Chart / Trading Reality (existing Next.js + TypeScript + PostgreSQL/Prisma production app)
**For:** Antigravity (or any coding agent working on the existing codebase)

---

## 0. The Problem (reported by the owner)

- One Google account was used on a PC to create many Trade Journal entries.
- The same Google account was then used to log in on a phone.
- **The journal entries created on the PC do not appear on the phone.**

A journal entry saved under a logged-in account must appear on every device where that same account logs in. Right now it doesn't, so user data is not reliably stored per-account in the database.

---

## 1. Rules for This Task

- **Diagnose first, with evidence. Do not guess and do not start rewriting.** Report what you actually find before changing anything.
- **Do NOT delete, clear, reset, or migrate-destructively any data** — in the database or in browser storage. The only copy of the owner's PC journals may currently exist in the PC browser's local storage. Losing it is the worst outcome.
- No fake/demo data. No frontend-only fixes. No second auth/user system. No rebuild.
- Reuse existing auth, Prisma models, and API architecture wherever they already exist.

---

## 2. Investigation (report findings for each step)

**Step 1 — Trace the journal write and read paths**
- From the "Log New Trade" / Journal Book UI: where does a saved entry actually go? Identify whether it is written to (a) `localStorage` / `sessionStorage` / IndexedDB / client state only, or (b) an API route → server logic → Prisma → PostgreSQL.
- Do the same for reading: where does the Journal page load its entries from?
- State clearly: is the database the source of truth for journals today, yes or no?

**Step 2 — Check account identity consistency**
- Does the same Google account on PC and on phone resolve to the **same User row and same User ID**? Look for duplicate users for one email, separate accounts created per provider/device, email case differences, or account-linking problems.
- Confirm that journal queries filter by the authenticated user's real ID from the server session.

**Step 3 — Check environment and database consistency**
- Compare `DATABASE_URL` (and any related env vars) across: the main site deployment, the admin deployment (`cycleofchartadmin`), Vercel Production vs Preview, and local development. Are there multiple databases?
- Is the owner's PC-created data present in the production database at all? Do a **read-only** check for journal rows linked to that user.

**Step 4 — Audit all user-owned data for the same problem**
Produce a table of every user-owned feature with columns: *Feature | Stored where today (DB / browser only) | Server-side auth enforced?*
Cover at least: Journal Books, Trade entries, Trade videos/screenshots, Daily Discipline, Private Trader Notebook, Workout Routine, Roadmap progress, profile/settings, leaderboard inputs.

**Step 5 — Admin Panel connectivity (verify only)**
- Confirm the admin app reads from the same production database as the main site, and that data created by real users on the main site is visible to it. Do not add new admin features in this task.

## 3. Fix (only after reporting the findings above)

- Make the **database the single source of truth** for all user-owned data found to be browser-only or inconsistent: real API routes with server-side authentication and per-user authorization → Prisma → PostgreSQL; the frontend reads from the API.
- Browser storage may remain only as a non-authoritative cache or UI preference — never as the only copy of user data.
- If duplicate user records or identity mismatches are found, fix the cause and reconcile safely without losing either record's data.
- If env/database mismatches are found, correct the configuration so all deployments that should share data use the same production database.

## 4. Data Rescue (must be done together with the fix)

- **Do not remove the local copy** until the server confirms the data is saved and readable back.
- Preserve original dates, P/L, notes, books, and attachments as faithfully as possible.
